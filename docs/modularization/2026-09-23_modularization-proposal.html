00Summary

go-etag is a monolith module whose five packages already form a clean layered DAG (entitytag ← server ← metrics, entitytag ← client, server ← root shim). The proposal makes the module boundary match the package boundary: four nested library modules (entitytag, server, client, metrics) plus a root module reduced to the deprecated shim. Every import path stays unchanged; consumers merely gain the ability to depend on less.

The bottom line Split is justified by three real composability seams (entitytag alone, client without server, server without client) and by keeping the root a deletable tombstone. It is enabled cleanly because the repo evolved into a strict DAG after the 2026-09-18 entitytag extraction and 2026-09-22 metrics move-in, which invalidated the 2026-08-16 “one go.mod” decision's premise of zero shared code between sides.

Why metrics gets a module despite zero standalone payoff metrics imports server, so no consumer can ever import metrics without server — the seam earns nothing by the composability test alone. But the alternatives are worse: keeping metrics in the root module makes the “tombstone deleted at v1.0.0” commitment impossible (the root would stay live forever), and moving the directory breaks the …/metrics import path. Under shared-version tagging the marginal cost is one extra tag per release.

03Strategy decisions

DAG verification

entitytag → {server, client}; server → {metrics, root}. No cycles possible: every edge points from consumer to a module with strictly fewer internal dependents. Verified by construction and by go mod graph after execution.

Workspace: go.work yes, replace never

Deviation from the skill's default dual strategy (go.work + replace), with rationale: this is a public proxy-published library. Committed replace + v0.0.0 requires are ignored by proxy consumers, whose resolution then fails on the nonexistent v0.0.0. The repo's release doctrine already bans replace directives (scripts/pre-release-check.sh:69). Instead: a committed go.work with all five use entries (workspace builds and CI never consult the proxy for in-repo modules), and sibling requires pinned at real released versions. GOWORK=off per-module builds are the published-state check and are run during the release staircase, not mid-cycle.

Versioning: shared version, bottom-up tag staircase

All modules release at the same vX.Y.Z (next: v0.6.0), matching the tight-coupled, single-team, single-train reality. Release order is dependency-first so each module's go.sum can be resolved from the proxy as it is finalized: tag entitytag/vX → tidy+verify+tag server/vX → client/vX → metrics/vX → root vX (the CHANGELOG-cut release commit). A module's tag points at the commit where its own go.mod/go.sum finalized; subtree content is identical across the staircase, which is all consumers see.

Error-type placement

All classified errors, codes, and templates stay in the server module (their only producer). The root tombstone keeps re-exporting ErrInvalidConfig as today. entitytag and client define no error types (client is clamp-don't-reject by design). No cross-module errors.Is surface changes.

Test isolation

All suites are same-package and move with their module untouched (server tests access unexported symbols; server/testutil_test.go is server-internal). The root shim's export-parity suite stays in the root module and requires the server module. No test-only module deps anywhere; go-error-family appears in server test files but is already a production dep of server.

07Build-system impact
