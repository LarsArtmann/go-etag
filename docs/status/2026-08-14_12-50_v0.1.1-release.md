## D) TOTALLY FUCKED UP

### D.1 — Used `--prerelease` on a Real Release

**This was a mistake.** The go-release skill says "Add `--prerelease` for v0.x releases or release candidates." I followed this literally, but the intent of that rule is for _actual_ pre-release versions (alpha, beta, rc) and 0.x _development_ releases where the API isn't stable. v0.1.0 was published as a regular (non-prerelease) Latest release, so v0.1.1 should have matched. Marking it as prerelease meant:

- `go get github.com/larsartmann/go-etag@latest` would still resolve to v0.1.0, not v0.1.1
- The GitHub release page showed "Pre-release" badge, discouraging adoption
- Inconsistency with v0.1.0's release status

**Root cause:** I blindly followed the skill's blanket rule for v0.x without checking what v0.1.0 did. The skill's rule is overly broad — "v0.x" should say "v0.x pre-release candidates (alpha/beta/rc)" or "first few 0.x releases if you're not confident in API stability." A patch release on top of a stable v0.1.0 is not a prerelease.

**Impact:** The release was live as prerelease for ~2 hours before the user caught it. During that window, `@latest` consumers got v0.1.0, not v0.1.1. Fixed by `gh release edit --prerelease=false --latest`.

**Lesson:** Always check the previous release's prerelease/latest status before creating a new one. Match the project's existing convention, not a blanket skill rule.

### D.2 — Tagged Before Fixing CI

**The v0.1.1 tag points at a commit with broken CI.** I ran local verification (build, test, lint, race) — all passed — but I didn't check whether CI was green on the remote before tagging. CI had been red since the very first push (`37b68b3` — the commit that added the CI workflow). Every single CI run in the repo's history had failed until I fixed the lint and fuzz jobs _after_ tagging.

I discovered the CI failures during post-push verification (Phase 6), then fixed them in three follow-up commits. But the tag was already on a commit with the broken workflow.

For a repo with CI, "pre-push verification" should include checking that the _last_ CI run was green, or at minimum that the CI workflow file is valid.

**Impact:** The tagged release has broken CI. Anyone cloning the tag and running the CI workflow gets failures. The code itself is correct (local verification passed), but the CI infrastructure at that commit is broken.

**What should have happened:** Check `gh run list` before tagging. See that CI is red. Fix the CI issues first. Commit the fixes. Then tag a commit that includes working CI.

## E) WHAT WE SHOULD IMPROVE

### E.1 — Check Previous Release Status Before Creating New One

Before creating any GitHub Release, query the previous release's `isPrerelease` and `isLatest` status. Match the project's convention. Don't blindly follow a skill rule about v0.x prereleases.

### E.2 — Check Remote CI Before Tagging

Add to the release pre-flight checklist: `gh run list --limit=3`. If CI is red, fix it BEFORE tagging. The tag should point at a commit with green CI. This is especially important when the CI workflow itself has never been green.

### E.3 — Understand Action Internals Before Configuring Them

When switching a GitHub Action's configuration (e.g., `install-mode: goinstall`), research what the action actually does with that setting. Read the action's source or docs. Don't guess — the action's `goinstall` mode constructs a specific `go install` path that may not work for v2 modules.

### E.4 — The go-release Skill's `--prerelease` Rule is Too Broad

The skill says "Add `--prerelease` for v0.x releases." This is misleading. A v0.1.1 patch release on top of a stable v0.1.0 is not a prerelease. The rule should be refined to: "Add `--prerelease` for alpha/beta/rc versions, or for initial 0.x releases if you're not confident in API stability. Once you've published a non-prerelease 0.x version, subsequent 0.x releases should match."

### E.5 — Squash CI Fixes Into Release Commit

When CI fixes are needed before a release, do them first, then squash everything (CI fixes + CHANGELOG) into one release commit. This ensures the tag points at a commit with working CI and a clean CHANGELOG. Multiple trial-and-error commits before a release is acceptable; multiple trial-and-error commits _around_ a tag is messy.

### E.6 — The v0.1.1 Tag Has Broken CI (Permanent)

Because tags are immutable on the Go module proxy, v0.1.1 will forever have the broken CI workflow at that commit. This can't be fixed without a v0.1.2. It's low-impact (consumers don't use `.github/`), but it means the repo's CI history shows: v0.1.1 tag → CI fails, then master → CI green. A future contributor cloning v0.1.1 and running CI would see failures.
